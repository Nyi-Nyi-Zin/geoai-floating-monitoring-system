# Maubin geospatial data workflow

The files under `raw/`, `reference/`, and `processed/` are local working data
and are intentionally ignored by Git.

## Inputs

- `raw/maubin_osm_waterways.geojson`: the user-supplied OpenStreetMap export.
- `raw/Copernicus_DSM_COG_10_N16_00_E095_00_DEM.tif`: active Copernicus DEM
  GLO-30 2021 tile covering Maubin. It is a 30 m digital surface model (DSM),
  not surveyed bare-earth elevation.
- `raw/Copernicus_DSM_COG_30_N16_00_E095_00_DEM.tif`: retained GLO-90 fallback
  tile; it is not used by the current terrain dataset.
- `raw/ESA_WorldCover_10m_2021_v200_N15E093_Map.tif`: official 2021 v200 10 m
  land-cover tile covering Maubin.
- `processed/maubin_esa_worldcover_10m_2021_v200.tif`: township-clipped
  WorldCover raster generated by the preparation command.
- `reference/maubin_township_boundary_mimu2020.geojson`: Maubin Township
  (`MMR017019`) queried in WGS84 from the public UNOSAT-hosted MIMU Township
  Boundary 2020 feature service.
- `raw/maubin-gfd-flood-history-2000-2018.geojson`: optional Google Earth
  Engine export produced by `scripts/gee_export_maubin_gfd.js`; it is not
  committed and must exclude permanent water before import.
- `raw/maubin-gfd-individual-events-2000-2018.geojson`: event-preserving export
  produced by `scripts/gee_export_maubin_gfd_events.js`. It retains DFO event
  IDs and start/end dates for temporal rainfall alignment.
- `raw/maubin-sar-individual-events.geojson`: optional Sentinel-1 SAR export
  produced by `scripts/gee_export_maubin_sar_events.js` for independent
  validation labels. See `docs/SAR_FLOOD_LABELS.md`.

OpenStreetMap data requires OpenStreetMap attribution and is subject to ODbL.
The MIMU boundary is for operational/reference use, must be attributed to MIMU,
and cannot be published on an online platform without MIMU's prior written
agreement. Replace it with a suitably licensed authoritative boundary before a
public production deployment if that permission is unavailable.

The terrain tile is available from the Copernicus DEM public AWS dataset. The
adapted terrain cells use this required notice:

> produced using Copernicus WorldDEM-30 © DLR e.V. 2010-2014 and © Airbus
> Defence and Space GmbH 2014-2018 provided under COPERNICUS by the European
> Union and ESA; all rights reserved

ESA WorldCover 2021 v200 is available from the official
<https://esa-worldcover.org/en/data-access> page and is licensed under
CC BY 4.0. Maps and adapted cell summaries retain this attribution:

> © ESA WorldCover project / Contains modified Copernicus Sentinel data (2021)
> processed by ESA WorldCover consortium

## Prepare the import file

From `backend/`:

```powershell
.\.venv\Scripts\python.exe -m scripts.prepare_osm_waterways `
  --source data/raw/maubin_osm_waterways.geojson `
  --boundary data/reference/maubin_township_boundary_mimu2020.geojson `
  --output data/processed/maubin_township_waterways.geojson `
  --segment-length-m 500
```

This filters to `river`, `stream`, `canal`, and `drain`, clips every geometry to
the township polygon, divides lines into monitoring segments of at most 500
metres in UTM zone 46N, preserves source identifiers and attribution, and
produces the schema accepted by the bulk-import API. The township boundary is
included as a separate asset for map rendering.

## Import

Start the API and run:

```powershell
.\.venv\Scripts\python.exe -m scripts.import_geojson `
  data/processed/maubin_township_waterways.geojson
```

Import is atomic and uses each Feature's stable `source_key` to update matching
assets. Re-running the same prepared dataset is therefore idempotent.

## Prepare the terrain grid

Apply migrations, then generate township-clipped terrain cells:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m scripts.prepare_terrain_grid --cell-size-m 500
```

The raw DEM remains at 30 m resolution. The command aggregates its pixels into
500 m display/analysis cells and stores the cell geometry, minimum/mean/maximum
elevation, local relief, relief-angle proxy, elevation percentile, and distance
to the mapped waterway network. Supported cell sizes are 100, 250, 500, and
1,000 metres.

These values describe terrain only. They are not flood probability, water
depth, or arrival-time predictions. A calibrated flood model still needs
rainfall, river-level/discharge observations, hydraulic connectivity, barriers,
drainage, and historical flood extents.

## Prepare land-cover composition

Apply migrations and run the WorldCover preparation from `backend/`:

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m scripts.prepare_land_cover `
  --source data/raw/ESA_WorldCover_10m_2021_v200_N15E093_Map.tif
.\.venv\Scripts\python.exe -m scripts.register_baseline_data_layers
```

The command clips the source to the township, stores the raster with its class
legend and licence notice, and updates every terrain cell with its dominant
class, pixel count, and percentage composition. Re-running it is idempotent.

WorldCover is a 2021 snapshot. Its classes are a useful explanatory input for
exposure and runoff/drainage analysis, but they are not current flood water and
are deliberately not included in the existing susceptibility score without
historical calibration.

## Prepare historical flood labels

Open `scripts/gee_export_maubin_gfd.js` in the Google Earth Engine Code Editor,
run it with an authorized Earth Engine project, and download the exported
GeoJSON from Google Drive into `data/raw/`. Then apply migrations and run the
provenance-aware importer documented in `backend/README.md`.

The current local database contains the exported Maubin GFD 2000–2018
frequency composite, clipped to the stored township boundary. Eight
non-empty frequency groups (1–8 observed events) cover 473.488 km² in total;
groups 9–14 from the larger export rectangle did not overlap the stored
township polygon and were deliberately skipped.

`scripts.train_flood_susceptibility` spatially intersects these labels with
all 5,549 terrain cells, exports the ignored
`data/derived/maubin_flood_ml_dataset_v1.csv`, evaluates a deterministic
spatial holdout, writes an ignored JSON model artifact under `artifacts/`, and
persists versioned cell probabilities to PostGIS. The binary training target
is historical flood coverage of at least 10% of a terrain cell.

The importer repairs polygon geometry, dissolves overlapping source features,
clips to the stored Maubin boundary, calculates geodesic area, and upserts by a
stable `source_key`. `--group-by-property event_count` preserves the spatial
frequency classes instead of dissolving them into one value. A `--dry-run`
option validates overlap without writing to PostGIS. Satellite-derived polygons
are training evidence only; dense
vegetation, buildings, clouds, permanent water, and source resolution can
create omissions or false detections.

For time-aware evaluation, import the individual-event file with
`python -m scripts.import_flood_events ...`, confirm
`GET /api/v1/flood-ml/event-readiness` is ready, then run
`python -m scripts.train_flood_event_model`. The active model version is
`maubin-flood-event-logistic-v5`. The dataset uses chronological holdouts,
never random cell rows from the same event across train and test.

Build the event metadata catalog after events are imported:

```powershell
.\.venv\Scripts\python.exe -m scripts.build_flood_event_catalog
.\.venv\Scripts\python.exe -m scripts.add_hand_features
```

Output: `data/derived/maubin_flood_event_catalog.json` (HAND, rainfall, terrain
stats per event).

For independent SAR validation labels, export with
`scripts/gee_export_maubin_sar_events.js`, import with
`python -m scripts.import_flood_sar_events`, evaluate with
`python -m scripts.evaluate_sar_label_validation`, and read
`docs/SAR_FLOOD_LABELS.md`.
